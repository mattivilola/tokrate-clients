# Tokrate desktop — Windows and Linux development

Tauri 2 uses the system webview, a Rust monitor, and a small React + TypeScript tray UI. The native Swift Mac client is maintained separately. This client is version **0.1.20, pre-release alpha**; do not advertise stable platform support until the acceptance checklist passes.

## Build

Install [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/), Rust stable and Node 22+. Linux additionally needs the Secret Service DBus development library (`libdbus-1-dev` on Ubuntu).

```
cd desktop
npm ci
npm test
npm run build
cargo test --manifest-path core/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml
npm run tauri -- build
```

Platform installers are built on their own OS by `.github/workflows/desktop.yml`. When `TAURI_SIGNING_PRIVATE_KEY` is available, CI produces updater-signed artifacts; pull-request builds without that secret remain unsigned test builds and are never published as releases. Windows NSIS and Linux AppImage installations can check the fixed alpha update feed and install only after the user clicks. Debian package installations use the manual download action because their privileged package replacement path has not been validated end to end. Local caches/target folders must not be committed. Keep Cargo and npm lockfiles once resolved. For a development UI server, use Portly as specified in root AGENTS.md. `npm run tauri -- dev` attaches to the managed preview at port 51719; it does not launch a second Vite process.

The browser preview labels its synthetic data and cannot upload it. A normal native launch uses real local logs and follows saved sharing preferences (new installations ask for consent; no community request or sharing-key access before acceptance). Update checks have a separate saved preference (new installation default ON); they never install without a click. Use the isolated smoke mode for automated tests:

```
python3 scripts/native-smoke.py src-tauri/target/release/tokrate-desktop
```

On Windows use the `.exe` suffix; on headless Linux wrap this in `xvfb-run -a dbus-run-session --`. The app requires an explicit temporary smoke directory, disables sharing and updater networking even if a command attempts to enable them, uses generated fixture logs, and exits after the webview validates parsed metrics. No production test data is sent.

## Boundaries

- `core`: Codex rollout JSONL, Claude Code transcript JSONL, Grok Build session event/usage logs, Antigravity conversation SQLite databases (read-only, bundled SQLite, a small protobuf wire reader), OpenCode's `opencode.db` (read-only, incremental, JSON paths extracted in SQL) and Kimi Code's `wire.jsonl` event logs (CLI and desktop app homes, incremental); normalized history, bounded monitors and signed samples/queue; independent of Tauri.
- `src-tauri`: credential manager, filesystem root, fixed HTTPS endpoints, network cancellation, native lifecycle and tray. Only normalized metrics reach the UI.
- **Monitoring cadence** (`src-tauri/src/watcher.rs`, `schedule.rs`, `runtime.rs`): one recursive folder watcher (`notify`, pinned) per existing source root reports what changed (re-spelled under the configured root, so a symlinked or canonicalized path still matches; bursts are coalesced for 0.5 s), and the monitors read only those files. A poll runs at the earliest time-based transition the core reports (a Claude parser flush, a delegated turn settling), every 2 s while a replay has data left, when a watcher or a setting change wakes it, and otherwise every 30 s so the live value ages out and Auto can switch model; never closer than 2 s, and a failed poll is retried after 2 s. The core enumerates the folders every 300 s as a safety net for missed events. Watchers are started before each poll for folders that exist and dropped when one vanishes. If one cannot start (for example the Linux inotify watch limit) it is logged once and that folder is rescanned every 30 s instead. Local history and the checkpoints of the files already read are written together (at most every 10 s while records arrive, when a replay finishes, and on exit), so a launch skips files the saved history covers; a crash only re-reads the files behind the unwritten records.
- `ui`: React 19 function components (see Interface below). Exact source/parser/metric/model/provider/version/effort cohorts, coding-tool and provider filters, independent turn-speed/first-token coverage, charts with gaps and local baselines. Claude and Grok do not report first-token time; their turn-speed definitions stay separate. No chart library, remote font, analytics SDK or browser-fetch transport (icons are bundled lucide SVGs).
- Sharing OFF clears the queue and community results, cancels the network task and prevents further identity/network work. Requests already transmitted cannot be recalled.
- Windows Credential Manager / Linux Secret Service hold signing keys. No plaintext-key fallback. Locked/unavailable credentials leave local monitoring operational; Retry starts a new future-only reporting period.
- Public API schema remains v1. Codex reports parser `codex-rollout-v1` / metric `turn-v1`; Claude Code reports `claude-transcript-v1` / `claude-observed-turn-v1`; Grok Build reports `grok-session-v1` / `grok-observed-work-turn-v1`. Antigravity reports `antigravity-conversation-v1` / `antigravity-observed-execution-v1` (data folder `~/.gemini`). OpenCode reports `opencode-db-v1` / `opencode-observed-turn-v1` (data folder `$XDG_DATA_HOME/opencode`, else `~/.local/share/opencode`). Kimi Code reports `kimi-wire-v1` / `kimi-observed-turn-v1` (homes `$KIMI_CODE_HOME`, else `~/.kimi-code`, and the Kimi desktop app's embedded home below its user-data folder). New adapters only share samples completed after consent and report no TTFT. The backend must accept 0.1.11 before upload testing with real observations.

## Interface

The UI follows `docs/design-language.md` (tokens, gauge, chart, vocabulary and the shared tray/popover information architecture).

- **Tray flyout** (window `main`, 380 x 640): header with mark, one model picker (coding-tool and provider filters live inside it) and a settings button; hero with the latest turn speed gauge, model, effort chip, Subagent chip, change against your 24 h median and relative time; trend with Turn speed / First token and 24 h / 7 d toggles plus a Details disclosure; "Your models" list (click to select, "Compare all" turns the list into the content with sort); community line only while sharing is on; footer with monitoring and sharing state and "Open tokrate.dev". Settings is an in-window view (General, Sharing, Sources, Updates, About and privacy). First launch is a three-step onboarding (welcome with detected sources, sharing choice with "See exactly what is sent", where to find Tokrate in the tray). The sharing notice opened from Settings is a modal sheet; closing it keeps sharing off.
- **Full history** (window `history`, 960 x 720, created on demand by the `open_history` command from the tray menu or Settings): larger chart, the numbers behind it and the bounded 500-row table. It is a second window instead of an in-window route so the flyout stays compact; both windows run the same bundle and the window label picks the surface. The `default` capability lists both labels.
- **Tray**: the tray value is the flyout hero's reading, computed by the same core function (`tray_reading`) with the flyout's selection, coding-tool filter and provider filter (the flyout reports its filters to the host): the live median of the followed model's last five responses while it responds, otherwise the response speed of its latest turn, otherwise the whole-turn speed for tools without response timing. "—" means nothing is measured in scope or monitoring is paused. The tooltip (all platforms) and the menu line name the measurement ("Response speed", "Response speed of the latest turn", "Turn speed of the latest turn"), the model, the provider and the coding tool. Text beside the icon (Linux and macOS development builds; Windows has no tray text) is led by the coding-tool chip, for example "CX 56.3 tok/s". Settings > General has "Show speed in tray", "Show provider badge" (the icon) and "Show coding tool chip" (default on; the tooltip always names the tool). The tray icon itself stays the provider badge: a two-letter chip does not stay legible in a 16 px icon.
- **Window behaviour** (`src-tauri/src/flyout.rs`): on Windows (and macOS for development) the flyout is undecorated, skipped in the taskbar, anchored above or below the tray icon inside the monitor work area, and hides on blur and on Escape. A tray click right after a blur-hide toggles it closed instead of reopening. Blur-hide is suppressed while the first-run choice is pending and while a native folder dialog is open. It stays hidden at launch unless the first-run choice is pending. Linux, and any desktop without a tray, keep an ordinary decorated window because tray visibility cannot be detected reliably. Tray-relative placement is implemented in-house (a pure, unit-tested function over the tray rectangle and the monitor work area) rather than with `tauri-plugin-positioner`, which avoids another dependency and keeps the geometry testable on every OS.
- **State**: `ui/store/store.ts` owns the Tauri command and poll layer behind a `useSyncExternalStore` subscription. Polls replace only the parts that changed, so mounted controls keep focus, scroll position and transitions; the existing `AsyncGate` still rejects reads that raced a newer mutation. `ui/model/dashboard.ts` and `ui/metrics.ts` hold the pure derivations and are covered by tests. Only normalized metrics and folder names cross into the webview; paths appear as compact folder names with the full path in a tooltip.
- **Dev preview**: `npm run dev` (Portly) serves a non-native preview with synthetic data, the "Development preview" notice and no network. Development builds honour `?scenario=default|empty|onboarding|sharing|update` and `?view=home|compare|settings|history`, for example `http://localhost:51719/?scenario=onboarding`, `?view=compare&scenario=sharing`, `?view=settings&scenario=update`, `?view=history`. Theme follows the OS (`prefers-color-scheme`).

## Remaining release acceptance

Record real Windows 11 and Linux GNOME/KDE desktop checks (including flyout placement next to the tray icon on every taskbar edge, hide-on-blur, tray toggle, the folder dialog while the flyout is open, Segoe UI Variable/Cantarell rendering and dark/light switching), key persistence/locked-store recovery, tray visibility/close/reopen/quit, high DPI/keyboard navigation, WSL/custom-folder behavior, idle CPU/RSS and installer upgrade/uninstall. CI native smoke covers startup/webview/fixture parsing; it is not a claim that every desktop integration passed. Windows Authenticode signing needs a separate verified signing arrangement. Resolve the service's existing legal/privacy launch findings before broad distribution. The full plan is in the private app repo `docs/WINDOWS_LINUX_PLAN.md`.
